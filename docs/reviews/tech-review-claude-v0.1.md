# 기술 검토 의견서: 작가용 창작 관리 플랫폼 (사업계획서 초안 v0.1)

- 작성: 개발 담당 Claude Opus (사업계획서 12.3 역할)
- 작성일: 2026-11-21
- 검토 대상: `감평툴 초안기획.txt` (14장 "개발 담당자 기술 검토 요청" 12개 항목)
- 범위: 기술 판단만 다룬다. 기획·UX/디자인·사업 영역(GPT, Gemini, 참깨빙수 담당)은 필요한 경우 한 줄로만 언급한다.
- 이번 단계에서는 코드 작성과 DB 구축을 하지 않았다. 노션은 열람·수정하지 않았다.

### 표기 규칙

- **[초안]** 사업계획서에 적힌 사실
- **[판단]** 개발 담당의 기술적 판단 또는 추론
- **[미확인]** 실험이나 자료로 확인하지 않은 가정. PoC(8.1 사전 기술 검증)에서 확인해야 한다.

## 0. 핵심 판단 요약

1. **[판단]** 원고·설정 관리 본체는 표준적인 웹 CRUD라 실현 가능성이 높다. 실패 위험은 AI 쪽에 몰려 있으며, 그중에서도 **동일 인물 판별(별칭 병합)**, **충돌 탐지의 오탐률**, **"인물이 알 수 없는 정보" 자동 탐지**가 가장 어렵다. 마지막 항목은 MVP에서 자동화를 포기하고 수동 기록으로 내려야 한다.
2. **[판단]** 데이터 모델의 중심은 "설정 항목" 테이블이 아니라 **근거·출처·상태·유효 구간을 가진 개별 진술(Assertion)** 테이블이어야 한다. 이 구조를 처음에 잘못 잡으면 6.2·6.3의 요구를 나중에 붙일 수 없다.
3. **[판단]** 안전 불변식 하나를 시스템 규칙으로 고정할 것을 제안한다. **"AI 작업과 백그라운드 작업은 후보(candidate)만 쓸 수 있고, 확정 데이터는 사용자 행동으로만 바뀐다."** 원고 수정 동기화, 모델 장애, 프롬프트 인젝션 대응이 모두 이 규칙 하나로 단순해진다.
4. **[판단]** 시뮬레이터는 "LLM은 회차별 전개 태그만 뽑고, 잔존율은 결정적 수식으로 계산"하는 구조가 맞다. 회차 태그를 원고 버전별로 캐시하면 독자 구성이나 시드를 바꿔 재실행해도 LLM 비용이 거의 들지 않는다. 기술 위험은 낮고, 위험은 "재미있느냐"라는 설계 쪽에 있다.
5. **[판단]** MVP 8개 항목은 여전히 크다. 충돌 탐지는 화이트리스트 속성(이름·나이·소속·직책·생사/부상)으로 좁히고, 지도·가상 달력·관계도·자동 승인 규칙·정보 습득 추적 자동화·BYOK와 운영자 모델 동시 지원은 MVP에서 빼야 한다.

## 1. 전체 제품 구상의 기술적 실현 가능성

| 영역 | 판단 | 근거 |
|---|---|---|
| 프로젝트·회차·버전·검색·내보내기 | 높음 | 일반적인 웹 서비스 기능이다. 한국어 전문 검색만 별도 처리가 필요하다(8절 참고). |
| 수동 설정집·위키·복선·연표 입력 | 높음 | 입력 UI와 데이터 모델의 문제이지 기술 난제는 아니다. 단, 사용자 정의 속성과 가상 달력은 범위를 잘못 잡으면 비용이 커진다. |
| AI 설정 추출 + 승인 | 중간 | 회차 단위 구조화 추출 자체는 현재 LLM으로 가능하다고 본다 **[판단]**. 다만 한국어 웹소설에서의 정밀도·재현율은 **[미확인]**이며, 수백 화 단위에서 같은 인물을 하나로 묶는 작업(별칭·호칭·직함 변화)이 실제 품질을 좌우한다. |
| 설정 충돌 탐지 | 낮음~중간 | 구조화된 속성 비교는 가능하다. 하지만 3.3이 스스로 인정하듯 회상·거짓말·오해·의도적 은폐 때문에 오탐이 많을 것이다 **[판단]**. 오탐이 많으면 사용자가 경고를 무시하게 되어 기능 가치가 사라진다. |
| 정보 습득 시점 추적 ("알 수 없는 정보 사용") | 낮음 | 인물별 지식 상태를 회차마다 추론해야 하고, 원고는 대부분 "누가 무엇을 아는지"를 명시하지 않는다. 자동 탐지는 MVP·2차에서 현실적이지 않다고 판단한다. 수동 기록 + 보조 질의로 축소를 권한다. |
| 시간선 (가상 달력, 상대 시간, 불명확 기간) | 중간 | 데이터로 저장하는 것은 가능하다. 그러나 모순 자동 검증까지 하려면 시간 제약 추론기가 필요하고 비용 대비 효용이 낮다. |
| 가상 연재 시뮬레이터 | 기술적으로 높음 | 4.6의 "AI는 분석, 수치는 별도 로직" 방향은 옳다. 기술 위험보다 설계 위험(결과가 납득되고 재미있는가)이 크다. |
| 세계관 생성 도구 (이름 생성, 랜덤표 등) | 높음 | 독립 모듈로 언제든 추가 가능하다. 우선순위의 문제다. |
| 지도 (업로드 이미지 + 핀) | 높음 | 3.6에서 이미 이미지 위 핀 방식으로 축소되어 있어 적절하다. MVP 대상은 아니다. |

**[판단]** 결론적으로 "전부 만들 수 있느냐"의 답은 예이지만, 제품 신뢰도를 좌우하는 것은 추출과 충돌 탐지의 **정밀도**다. 이 수치는 실제 원고로 PoC를 돌리기 전에는 아무도 모른다. 따라서 8.1 사전 기술 검증을 형식적 단계가 아니라 **진행/중단 판단 단계(go/no-go)**로 운영해야 한다.

## 2. 구현 난도가 가장 높거나 실패 위험이 큰 기능

위험이 큰 순서로 정리한다.

### 2.1 동일 개체 판별 (Entity Resolution)
- **[판단]** "민수", "김 대리", "형", "그 남자", "검은 기사"가 같은 인물인지 판정하는 일이다. 한국어에서는 조사가 붙은 형태("민수가", "민수는")와 호칭·직함 변화가 많아 단순 문자열 비교로는 부족하다.
- 잘못 병합하면 두 인물의 설정이 섞이고, 잘못 분리하면 같은 인물에 대한 충돌을 못 잡는다. 이후 모든 기능(충돌, 연표, 복선, 시뮬레이터 선호 인물)이 이 결과 위에 올라간다.
- **대안:** 회차 분석 전에 "인물 명부(roster)"를 작가가 먼저 확정하는 단계를 둔다(4절의 2단계 추출). 명부에 없는 이름은 "신규 개체 후보"로만 올린다.

### 2.2 설정 충돌 탐지의 오탐
- **[판단]** 6.2의 진술 유형(서술/발언/작가 확정/아이디어)을 구분하지 않으면 거짓말과 회상이 전부 충돌로 잡힌다. 구분하더라도 화자 판별(누가 한 말인가)이 한국어 소설에서 자주 생략되어 정확도가 떨어질 수 있다 **[미확인]**.
- **대안:** MVP 충돌 대상은 정형 속성 몇 개로 제한하고, 경고마다 양쪽 원문 인용을 붙이며, "의도된 전개"로 분류한 경고의 키(개체+속성+값 쌍)를 저장해 재발을 막는다(3.3의 반복 경고 최소화 요구를 이렇게 구현).

### 2.3 정보 습득 시점 추적
- 1절에서 본 대로 자동화 난도가 매우 높다. 2.1과 2.2가 먼저 안정되어야 시도할 수 있다.
- **대안:** `지식 기록(인물, 진술, 알게 된 회차, 근거)`을 수동 입력으로 제공하고, AI는 "이 장면에서 A가 B 사실을 언급함"을 후보로만 제안한다. 위반 탐지는 3차 이후.

### 2.4 원고 수정 시 근거 위치 유지
- 근거를 "문자 오프셋"으로만 저장하면 앞부분 한 줄만 고쳐도 이후 근거가 전부 어긋난다. 5절에서 대응 방법을 다룬다.

### 2.5 대량 초기 등록 시 검토 피로
- **[판단]** 300화짜리 기존 연재작을 등록하면 후보가 수천 건 나올 수 있다 **[미확인: 실제 건수는 PoC에서 측정]**. 작가가 이를 하나씩 승인하지 않으면 "AI 추출은 승인 후에만 확정"이라는 원칙 때문에 위키가 비어 있게 된다.
- 이 문제는 기술과 UX가 겹친다. 기술 쪽 대안은 후보 묶음 처리(개체별 일괄 승인, 출현 빈도·신뢰도 정렬, 동일 사실 중복 병합)이고, 화면 설계는 Gemini 담당이다.

### 2.6 성인·고자극 장르에서의 모델 거부
- **[판단]** 피폐물·NTR·고수위 작품은 외부 모델이 분석을 거부하거나 내용을 순화해 요약할 수 있다 **[미확인: 모델·공급사별로 다름]**. 초안이 예시로 든 장르(4.2, 4.5)가 정확히 이 영역이라 실제 이용자층과 겹친다.
- 거부를 "작업 실패" 상태로 정상 처리해야 하고, 장르별로 PoC 테스트셋에 포함해야 한다.

## 3. 원고·설정·사건·인물 상태 데이터 모델

**[판단]** PostgreSQL 단일 DB로 충분하다. 그래프 DB나 별도 벡터 DB는 MVP에 필요 없다. 아래는 스키마 확정이 아니라 구조 제안이다.

### 3.1 원고 계층
```
Project ─┬─ Chapter (안정 ID, 표시 회차번호, 정렬키, 제목, 메타)
         │     └─ ChapterVersion (불변, 본문, 내용 해시, 생성 시각, 업로드 출처)
         │           └─ Segment (문단/장면 단위, 버전 내 순번, 텍스트, 해시)
         └─ ...
```
- Chapter의 **ID, 표시 회차번호, 정렬키를 분리**한다. 3.1의 "등록 순서와 실제 회차 번호의 분리" 요구와 11.1의 "순서를 바꿔도 설정이 유지되는가"를 이렇게 충족한다.
- ChapterVersion은 수정하지 않고 새로 쌓는다(원본 보존). 본문은 DB 텍스트 컬럼으로 충분하다 **[판단: 1화 수천~1만 자 수준이면 오브젝트 스토리지 분리가 필요 없음]**. 원본 업로드 파일(DOCX 등)만 오브젝트 스토리지에 둔다.

### 3.2 설정 계층: 개체와 진술
```
Entity (id, project, 종류: 인물/조직/지역/물건/사건/능력/법칙/사용자정의,
        대표명, 상태: 후보/확정/병합됨/폐기)
EntityAlias (entity, 별칭 문자열, 정규화형, 출처)
AttributeDef (project, entity 종류, 키, 표시명, 값 타입, 시간 가변 여부)

Assertion  ← 핵심 테이블
  id, project
  subject_entity        (누구/무엇에 대한)
  attribute_key         (나이, 소속, 생사 등) 또는 relation(대상 entity, 관계 종류)
  value                 (JSONB, AttributeDef 타입으로 검증)
  source_type           (원고 서술 / 인물 발언 / 작가 확정 / 작가 미확정 아이디어 / AI 추론)
  speaker_entity        (발언인 경우 화자)
  status                (후보 / 확정 / 보류 / 거부 / 재검토 필요)
  valid_from, valid_to  (이 값이 참인 구간: 회차 범위 또는 작품 내 시간)
  supersedes            (이전 진술 ID, 덮어쓰지 않고 연결)
  created_by            (사용자 / AI 작업 ID)
Evidence (assertion, chapter_version, segment, 인용문, 앞뒤 문맥, 오프셋)
ChangeLog (대상, 이전값, 이후값, 행위자, 시각, 사유)
```
- **[판단]** 6.2의 여섯 가지 정보 종류는 `source_type × status` 두 축으로 표현된다. "검토 결과 부정되거나 폐기된 정보"는 별도 종류가 아니라 status=거부다.
- **인물 상태 변화**(부상, 사망, 복귀)는 별도 테이블이 아니라 `attribute_key=상태`인 Assertion이 `valid_from/valid_to`를 가지는 것으로 표현한다. "현재 상태"는 최신 확정 진술을 조회한 결과다.
- **사용자 정의 속성**은 EAV(행마다 속성 하나)로 가면 쿼리가 복잡해지므로, 정의는 `AttributeDef`에, 값은 Assertion의 JSONB에 둔다. 시간에 따라 바뀌지 않는 단순 메모성 필드는 Entity의 JSONB 컬럼으로 충분하다.

### 3.3 사건·시간
```
Event (Entity의 한 종류)
StoryTime (event, 달력 ID, 시작/끝(정밀 또는 범위), 정밀도, 원문 표현 문자열, 상대 기준 사건)
Reveal (event, 공개 회차, 근거)              ← "독자에게 공개된 순서"
Knowledge (인물, assertion 또는 event, 알게 된 회차/시점, 근거)  ← MVP는 수동
```
- **[판단]** 가상 달력은 MVP에서 "원문 표현 문자열 + 작가가 정한 정렬키"만 저장하면 충분하다. 달력 체계 정의(월 수, 연호 변환)는 3차로 미룬다. 정렬키만 있으면 연표 정렬은 된다.

### 3.4 AI 작업과 시뮬레이션
```
AnalysisJob (종류, 대상 chapter_version, 모델, 프롬프트 버전, 상태, 토큰, 비용, 오류)
Candidate → Assertion(status=후보)로 저장. 별도 테이블을 두지 않는다.
ChapterFeatures (chapter_version, 추출기 버전, 태그 목록 JSON, 근거 인용)  ← 시뮬레이터 공용 캐시
Persona, Cohort, SimulationRun (설정, 시드, 원고 버전 스냅샷), SimulationStep (회차별 집단 상태)
GeneratedComment (run, 회차, 페르소나, 본문, 참조 근거)
```

## 4. 장편 원고 분석과 자동 설정 추출의 현실적 방법

### 4.1 입력 규모 **[추정]**
- 웹소설 1화를 5,000~6,000자 정도로 보면 300화는 150만~180만 자다. 한국어의 토큰 환산 비율은 모델 토크나이저마다 달라 **[미확인]**이다. 비용 계산식은 7절에 둔다.
- 어느 경우든 전체 원고를 한 번에 넣는 방식은 맞지 않다는 7.2의 판단에 동의한다.

### 4.2 권장 파이프라인
1. **정규화·분할 (AI 없음):** 인코딩 정리, 회차 경계 인식(제목 패턴 정규식 + 사용자 확인), 문단 단위 Segment 분할, 해시 계산.
2. **1단계: 이름 수집 (병렬, 저가 모델):** 회차마다 고유명사·호칭 후보만 뽑는다. 전체 회차를 병렬로 돌려도 순서 의존성이 없다.
3. **명부 정리 (사용자 확인):** 출현 빈도와 동시 출현 정보로 별칭 묶음을 제안하고, 작가가 주요 인물 명부를 확정한다. 2.1 위험을 여기서 줄인다.
4. **2단계: 사실 추출 (병렬, 회차 단위):** 확정 명부를 프롬프트 앞부분(캐시 대상)에 넣고, 회차 본문에서 고정 JSON 스키마로 진술을 추출한다. 각 진술에 인용문을 반드시 포함시키고, 서버가 그 인용문이 실제 본문에 존재하는지 문자열로 검증한다. 존재하지 않으면 폐기한다(환각 방지 장치이자 근거 연결 방법).
5. **비교 (대부분 AI 없음):** 추출 진술과 확정 진술을 (개체, 속성) 키로 비교해 신규/동일/상이로 분류한다. 상이한 것 중 화이트리스트 속성만 충돌 후보로 올린다. 필요할 때만 상위 모델로 "회상·발언·시점 변화로 설명되는가"를 2차 판정한다.
6. **검토 대기열:** 모든 결과는 후보로만 저장된다.

### 4.3 장편 맥락 처리
- **[판단]** 회차 단위 추출은 앞선 맥락이 없어 "그"가 누구인지 놓칠 수 있다. 대응은 (a) 명부 주입, (b) 직전 1~2화의 짧은 요약을 맥락으로 제공, (c) 대명사 해소는 무리하게 시도하지 않는 것이다.
- 요약은 맥락 보조로만 쓰고 근거로는 쓰지 않는다(7.2 원칙과 일치). 근거는 항상 원문 인용이다.

### 4.4 검색
- **[판단]** MVP 검색은 PostgreSQL 전문 검색으로 시작한다. 단 PostgreSQL 기본 전문 검색은 한국어 형태소 분석을 지원하지 않으므로 `pg_trgm`(삼중자 유사도) 또는 `pg_bigm` 계열 확장으로 부분 문자열 검색을 구현한다. 관리형 DB에서 어떤 확장을 쓸 수 있는지는 공급사별로 **[미확인]**이다.
- 벡터 검색(pgvector)은 "비슷한 장면 찾기"나 복선 회수 후보 탐색에 쓸모가 있으나 MVP 필수는 아니다.

## 5. 수정 원고와 기존 설정의 안전한 동기화

### 5.1 원칙
- **불변식 1:** ChapterVersion은 수정·삭제하지 않는다. 새 버전만 추가한다.
- **불변식 2:** 백그라운드 작업은 확정 진술(status=확정)을 바꾸거나 지우지 못한다. 상태를 "재검토 필요"로 바꾸는 것만 허용한다.
- **불변식 3:** 작가 메모와 수동 설정은 원고가 아니라 개체(Entity)에 붙는다. 그래서 원고 재등록으로 사라질 수 없다(3.1 요구).

### 5.2 근거 재고정(Re-anchoring)
- Evidence는 오프셋만이 아니라 **인용문 + 앞뒤 문맥(각 30~50자)**을 함께 저장한다. 웹 표준 주석(W3C Web Annotation의 TextQuoteSelector)과 같은 방식이다.
- 새 버전이 들어오면 각 근거를 다음 순서로 다시 찾는다.
  1. 같은 Segment 해시가 새 버전에 있으면 위치만 옮긴다(변경 없음).
  2. 없으면 인용문을 새 본문에서 정확히 검색하고, 여러 곳이면 앞뒤 문맥으로 고른다.
  3. 그래도 없으면 유사 문자열 검색으로 후보 위치를 찾고, 유사도가 기준 미만이면 "근거 유실"로 표시한다.
- 근거가 유실된 확정 진술은 삭제하지 않고 "재검토 필요"로 전환한다(6.3 요구와 일치).

### 5.3 재분석 범위
- 바뀐 Segment가 있는 회차만 2단계 추출을 다시 돌린다. 이전 버전의 추출 결과와 비교해 "새로 생긴 후보 / 사라진 근거 / 값이 바뀐 진술"만 검토 대기열에 올린다.
- 결과 캐시 키는 `(Segment 또는 회차 내용 해시, 프롬프트 버전, 모델)`이다. 내용이 같으면 다시 호출하지 않는다.
- 이 회차를 참조한 시뮬레이션 결과와 충돌 경고는 자동 재계산하지 않고 "이전 버전 기준" 표시만 한다. 재실행은 사용자 선택이다(비용 통제).

### 5.4 작업 실패와 복구
- 작업은 회차 단위로 쪼개고, 각 작업은 같은 입력으로 다시 실행해도 결과가 중복되지 않게(멱등) 만든다. 일괄 등록 중 일부가 실패해도 실패한 회차만 재시도한다(11.1의 "일부 실패 시 복구" 요구).

## 6. 독자 페르소나와 연독 시뮬레이션 계산 방법

### 6.1 구조
```
[회차 원문] → (LLM, 버전당 1회, 캐시) → 회차 전개 태그
[작품 약속 프로필] (장르·태그·소개문 기반, 작가 확인)
[독자 집단 상태] + [집단별 선호 가중치표] → (결정적 수식) → 만족도·잔존 인원
[집단 상태 + 회차 태그 + 근거 인용] → (LLM, 회차당 1회 묶음 호출) → 댓글·감상평
```

### 6.2 회차 전개 태그 (LLM 담당)
- 고정된 태그 분류표에서 고르고 강도(0~3)와 근거 인용을 붙인다. 예시: `주인공_활약`, `보상_획득`, `고구마`, `사이다`, `연애_진전`, `관계_배신`, `장르약속_위반(종류)`, `인기인물_퇴장`, `설명_과다`, `복선_회수`, `반전`, `비극`.
- **장르 약속 위반**은 회차마다 LLM이 장르를 추론하지 않게 한다. 작품 단위 "약속 프로필"(예: 순애, 1:1, 먼치킨)을 작가가 확인해 두고, 태그가 그 프로필과 충돌하는지만 판단한다. 4.5의 사례들이 이 방식으로 처리된다.
- 태그 분류표 자체의 구성은 기획 영역이다(GPT 담당). 개발 쪽 요구는 "닫힌 목록이어야 하고 버전 관리되어야 한다"는 것뿐이다.

### 6.3 집단 상태와 계산 (결정적 로직 담당)
집단 c의 회차 t 상태: 인원 `N_c,t`, 만족도 `S_c,t`, 신뢰도 `T_c,t`, 누적 불만 `F_c,t`.

```
기여도_c,t   = Σ_태그 ( W[c][태그] × 강도_태그 )
F_c,t        = F_c,t-1 × 감쇠_F + 고구마류 기여(음수분)  − 사이다/보상 시 해소량
S_c,t        = S_c,t-1 × α + (1−α) × 기준선_c + 기여도_c,t − λ × F_c,t
T_c,t        = T_c,t-1 + (장르약속 위반 시 큰 감소, 복선 회수 시 소폭 증가)
이탈확률_c,t = 기본이탈(t) + (1 − 기본이탈(t)) × σ( k × (θ_c − S_c,t − μ × T_c,t) )
N_c,t        = N_c,t-1 × (1 − 이탈확률_c,t)  (+ 고급 모드의 유입_c,t)
```
- `W[c][태그]`는 페르소나별 선호 가중치표다. 예: 피폐물 선호 집단은 `비극`에 양수, 순애 집단은 `관계_배신`에 큰 음수. 이렇게 하면 4.5의 "비극이 오류가 아니며 선호 독자의 만족도는 오를 수 있어야 한다"는 요구가 자연스럽게 충족된다.
- `기본이탈(t)`은 회차가 지날수록 자연스럽게 줄어드는 기본 하차 곡선이다. 실제 연재 통계에 근거한 값이 아니라 **조정 가능한 파라미터**로 두고, 그렇게 표시한다 **[판단: 실측 근거 없음]**.
- **이탈 사유**는 계산 과정에서 태그별 기여도를 저장해 두면 그대로 나온다. "이번 회차 순애 집단 이탈의 62%는 `관계_배신`에서 발생" 같은 설명이 LLM 없이 가능하다(4.6의 설명 가능성 요구).
- **집단별 선호 인물 변화**는 `인물별 호감도` 벡터를 집단 상태에 두고, 태그가 특정 인물과 연결될 때 갱신한다. 2차 기능으로 둔다.

### 6.4 난수와 재현성
- **[판단]** 초안 4.6은 시드 저장을 요구한다. 그런데 10,000명을 이항분포로 뽑으면 큰 수의 법칙 때문에 시드를 바꿔도 곡선이 거의 같아 시드 변경이 의미가 없다.
- 그래서 무작위성은 인원 표본이 아니라 **실행 단위 파라미터**에 넣는다. 시드로 가중치 W, 임계값 θ에 작은 섭동을 주고, 댓글 생성 시 대표 페르소나 선택에 쓴다. 같은 시드와 같은 원고 버전, 같은 설정이면 수치는 완전히 같다. 댓글은 LLM 출력이라 완전 재현이 보장되지 않으므로 생성 결과를 저장해 재표시한다.

### 6.5 연속 독서 기억
- 집단마다 짧은 "기억 요약"(수백 토큰 상한)을 두고 회차마다 갱신한다. 기억 내용은 회차 태그와 근거 인용에서 만든다. 원문 전체를 매번 다시 읽히지 않는다.
- 중간 유입 독자는 유입 회차부터 상태를 시작하면 되므로 별도 구현 부담이 적다.

### 6.6 댓글 생성
- 대표 페르소나 여러 명의 댓글을 **회차당 한 번의 호출**로 묶어 생성한다. 입력은 집단 상태 요약, 회차 태그와 인용문, 짧은 회차 요약이다.
- "원고에 없는 장면을 지어내어 비판"(4.2)을 줄이기 위해 댓글이 언급하는 사건은 태그 근거 목록 안에서만 고르도록 지시하고, 인용을 포함한 댓글은 서버에서 원문 존재 여부를 검사한다.
- 페르소나끼리 의견을 주고받는 댓글창은 호출 수가 크게 늘어나므로 2차로 둔다(초안 8.3과 일치).

### 6.7 비용 구조의 이점
- 회차 태그는 원고 버전별로 한 번만 만든다. 이후 독자 구성, 비율, 시드, 가중치를 바꿔 재실행하는 비용은 **댓글 생성분뿐**이고, 댓글을 끄면 LLM 호출이 0회다. 4.4의 "10,000회 호출하지 않는다"보다 한 단계 더 줄어든다.

## 7. AI 모델 호출 비용 절감 설계

1. **결과 캐시를 1급 설계로:** 모든 AI 결과의 키를 `(입력 내용 해시, 작업 종류, 프롬프트 버전, 모델)`로 둔다. 같은 원고에 같은 작업을 두 번 돈 비용은 0이어야 한다.
2. **작업별 모델 분리:** 이름 수집·태그 추출은 저가 모델, 충돌 2차 판정과 댓글은 상위 모델. 어떤 모델이 어느 작업에 충분한지는 **[미확인]**, PoC에서 정확도 대비 단가로 결정한다.
3. **프롬프트 캐싱:** 명부·스키마·지시문처럼 회차 간 같은 앞부분을 프롬프트 앞에 고정해 공급사의 프롬프트 캐싱을 쓴다. 공급사마다 할인율과 조건이 다르다 **[미확인: 현재 요금표 확인 필요]**.
4. **배치 API:** 초기 일괄 등록처럼 실시간이 아닌 작업은 공급사의 배치 처리(할인 + 지연 허용)로 보낸다. 지원 여부와 할인율은 공급사별 **[미확인]**.
5. **AI 없이 먼저 거르기:** 회차 경계, 별칭 문자열 매칭, 같은 값 비교, 인용문 존재 검증은 코드로 처리한다. LLM에는 판단이 필요한 것만 보낸다.
6. **사전 견적:** 실행 전에 `회차 수 × 평균 글자 수 × 토큰 환산비 × 작업 수 × 단가`로 예상 비용을 보여 주고, 사용자별·작품별 상한과 작업 취소 기능을 둔다(7.4 요구).
7. **원가 계측:** AnalysisJob에 입력·출력 토큰, 캐시 적중, 비용을 기록해 기능별 원가를 바로 집계할 수 있게 한다(7.4, 11.3 요구). 수치 없이 요금제를 정하지 말라는 9.3의 원칙과 맞물린다.

## 8. 권장 프론트엔드·백엔드·데이터베이스·배포

**[판단]** 인원이 적고 유지보수 부담을 줄여야 하므로 **TypeScript 하나로 통일한 모놀리식 + 별도 워커 프로세스**를 권한다.

| 구성 | 권장 | 이유 / 대안 |
|---|---|---|
| 프론트엔드 | Next.js + React + TypeScript | 초안 후보와 같다. 반응형 웹 요구(5.3)에 맞다. |
| 백엔드 API | Next.js 서버 기능 또는 같은 저장소의 Node API (Fastify 등) | 언어를 하나로 두면 타입·검증 스키마를 공유할 수 있다. Python은 한국어 형태소 분석(예: kiwipiepy)이 꼭 필요해질 때 보조 서비스로만 추가한다. |
| DB | PostgreSQL (관리형) | JSONB, 전문 검색 확장, pgvector, 행 수준 보안(RLS)을 한 곳에서 해결한다. 그래프 DB·별도 벡터 DB는 불필요하다. |
| 작업 큐 | PostgreSQL 기반 큐 (pg-boss, Graphile Worker 류) | Redis를 추가하지 않아도 된다. 처리량이 커지면 그때 교체한다. |
| 워커 | 장시간 실행 가능한 별도 프로세스 | 서버리스 함수는 실행 시간 제한이 있어 일괄 분석에 맞지 않는다. 프론트를 서버리스에 올리더라도 워커는 상시 프로세스로 둔다. |
| 파일 저장 | S3 호환 오브젝트 스토리지 | 원본 업로드 파일과 내보내기 파일만 저장한다. |
| 파일 파싱 | TXT/MD 직접 처리, DOCX는 mammoth 등 | EPUB·PDF는 초안대로 보류한다. |
| 인증 | 관리형 인증 서비스 또는 검증된 라이브러리 | 직접 구현하지 않는다. |
| LLM 연동 | 자체 얇은 추상화 계층 (작업 → 모델 매핑, 구조화 출력 검증) | 7.3 요구. 무거운 에이전트 프레임워크는 필요 없다. |
| 차트 | Recharts 등 일반 차트 라이브러리 | 연독률 그래프 용도로 충분하다. |
| 배포 | 관리형 PaaS 한 곳에 웹·워커·DB를 모으는 구성 | 초기에는 운영 표면을 줄이는 것이 비용보다 중요하다. 특정 공급사 선정은 비용 비교 후 결정한다 **[미확인]**. |

- **데스크톱·오프라인(13장 결정사항):** 기술적으로는 웹 우선에 동의한다. 다만 나중에 오프라인을 할 가능성이 있으면 지금부터 ID를 UUID로 쓰고 서버 생성 순번에 의존하지 않는 것이 좋다. 비용이 거의 들지 않는 대비책이다.

## 9. MVP에서 반드시 제외하거나 축소할 기능

### 9.1 제외 권고
| 기능 | 이유 |
|---|---|
| 정보 습득 시점 위반 자동 탐지 | 2.3. 정확도를 낼 수 없고 오탐이 신뢰를 깎는다. |
| 이동 시간·장소 불일치, 능력 제한조건 위반 탐지 | 세계관 규칙을 기계가 읽을 수 있는 형태로 먼저 입력받아야 하므로 MVP 비용이 크다. |
| 가상 달력·연호 체계 정의 | 원문 표현 + 정렬키로 대체한다. |
| 지도, 관계도·조직도 시각화 | 독립 모듈이라 나중에 붙여도 된다(8.5와 일치). |
| AI 자동 승인 규칙 (3.2) | 잘못 설정하면 확정 데이터가 오염된다. 일괄 승인 UI로 대체한다. |
| BYOK와 운영자 모델 동시 지원 | 둘 다 지원하면 키 보관·모델별 품질 차이·비용 정산 경로가 두 배가 된다. 하나를 고른다(12절 참고). |
| 페르소나 간 대화형 댓글창, 재유입 고급 모드 | 초안도 2차로 두었다. 동의한다. |
| EPUB·PDF, 외부 프로그램 가져오기, 공동 편집, 시리즈 공유 세계관 | 초안과 같은 판단. 단, 시리즈 공유를 장기적으로 할 것이라면 Entity의 소속 범위(작품/시리즈)를 데이터 모델에 미리 열어 둔다. |

### 9.2 축소 권고
| 기능 | 축소안 |
|---|---|
| 설정 충돌 후보 탐지 | 이름·나이·소속·직책·생사/부상 상태만 대상으로. |
| 사용자 정의 설정 항목 | MVP는 개체별 자유 키-값 필드만. 타입 정의·템플릿 편집기는 2차. |
| AI 설정 추출 | 인물·조직·지역 3종 우선. 물건·능력·법칙은 2차. |
| 가상 연재 | 기본 페르소나 프리셋 + 비율 조정 + 잔존율 곡선 + 회차당 묶음 댓글. 사용자 페르소나 생성은 프리셋 파라미터 조정 수준으로. |
| 복선 | 수동 등록·상태 관리만. AI 회수 후보 제안은 2차(초안과 일치). |

- **[판단]** 시뮬레이터는 설정집·충돌 탐지에 의존하지 않고 회차 원문과 약속 프로필만 있으면 돌아간다. 따라서 병렬로 개발할 수 있다. 어느 쪽을 먼저 내보일지는 사업 판단이다(참깨빙수·GPT 영역).

## 10. 권장 개발 순서와 의존성

```
0. PoC (8.1) ─ 테스트 원고 확보 + 정답 라벨 일부 작성
   │
1. 원고 계층 (Project/Chapter/Version/Segment, 업로드·분할·검색·버전)
   │
2. 설정 계층 (Entity/Alias/Assertion/Evidence/ChangeLog) + 수동 위키
   │            └─ 원문 드래그로 근거 연결하는 수동 기능 포함
   │
3. 작업 인프라 (큐·워커·LLM 추상화·비용 기록·캐시)
   │
   ├─ 4. AI 추출 → 후보 → 검토 대기열 (1·2·3 필요)
   │      │
   │      ├─ 5. 충돌 후보 (화이트리스트) (4 필요)
   │      └─ 6. 수정 원고 동기화 / 근거 재고정 (1·2·4 필요)
   │
   └─ 7. 회차 전개 태그 추출 (1·3 필요, 2와 무관)
          │
          8. 시뮬레이션 엔진 (순수 함수, 단위 테스트 우선)
          │
          9. 댓글·감상평 생성
   
10. 내보내기 (JSON 전체 + Markdown 위키 + CSV) ─ 2 이후 언제든
```
- 2단계에서 **AI 없이도 쓸 수 있는 수동 위키**를 먼저 완성하면 1.2의 "AI 없이도 기본 기능 동작" 원칙을 처음부터 검증할 수 있다.
- 6단계(동기화)를 뒤로 미루면 안 된다. 4단계 직후에 바로 붙여야 한다. 실제 작가는 업로드 후 곧바로 원고를 고치기 때문이다 **[판단]**.
- 8단계 시뮬레이션 엔진은 LLM 없이 가짜 태그로 단위 테스트할 수 있다. 11.2의 "같은 조건에서 재현 가능한가, 잔존율 계산에 논리 오류가 없는가"를 자동 테스트로 확인한다.

### 10.1 PoC에서 확인할 것과 통과 기준(제안)
- 장르가 다른 실제 원고 3편 이상, 각 50화 이상. 저작권 문제가 없는 원고 확보가 선결 과제다 **[미확인: 확보 경로 미정]**.
- 20화 분량에 사람이 정답(인물·속성)을 라벨링하고 추출 정밀도·재현율을 측정한다.
- 충돌 후보의 유효 비율(작가가 실제 문제로 인정한 비율)을 측정한다.
- 회차당 토큰·비용·소요 시간을 측정해 7절 견적식의 계수를 채운다.
- 고자극 장르에서 모델 거부율을 측정한다(2.6).
- 통과 기준 수치는 GPT·참깨빙수와 합의가 필요하다.

## 11. 주요 보안 위험과 운영 문제

| 위험 | 대응 |
|---|---|
| 다른 사용자 원고 노출 (테넌트 격리 실패) | 모든 테이블에 project/user 소유 키를 두고 DB 행 수준 보안(RLS) 또는 저장소 계층에서 강제한다. "다른 사용자 ID로 접근 시 거부"를 자동 테스트로 고정한다. |
| 원고 속 문장이 AI 지시로 작동 (프롬프트 인젝션, 7.5) | LLM에 도구 실행 권한을 주지 않는다. 출력은 JSON 스키마로 검증하고 후보로만 저장한다(불변식 2). 이 구조에서는 인젝션이 성공해도 "이상한 후보" 이상이 되지 않는다. |
| BYOK API 키 유출 | 키를 서버에서 암호화(관리형 KMS)해 보관하고, 클라이언트로 되돌려 보내지 않으며, 로그와 오류 메시지에서 제거한다. MVP에서 BYOK를 하지 않으면 이 위험 자체가 사라진다. |
| 업로드 파일 공격 | DOCX는 ZIP 기반이라 압축 폭탄·XML 외부 엔티티(XXE) 위험이 있다. 크기·압축 해제 용량 상한을 두고 외부 엔티티를 끈 파서를 쓴다. |
| 로그에 원고 본문 기록 | 7.3 원칙대로 본문·키를 일반 로그에 남기지 않는다. LLM 요청 로그는 해시와 길이만 남긴다. |
| 외부 AI 공급사의 데이터 보관·학습 | 공급사별 보관 기간·학습 사용 여부를 확인해 고지한다. 현재 각 공급사 정책은 **[미확인]**이며, 공급사 선정 시 확인 항목으로 둔다. |
| 모델 장애·거부 | 작업 상태로 처리하고 재시도·대체 모델을 둔다. 확정 데이터는 영향받지 않는다(불변식 2). |
| 비용 폭주 (오남용, 무한 재시도) | 사용자·작품 단위 상한, 재시도 횟수 제한, 일괄 작업 취소 기능. |
| 백업과 계정 삭제의 충돌 | 시점 복구(PITR) 백업을 쓰면 삭제된 원고가 백업 보존 기간 동안 남는다. 이 기간을 정책에 명시해야 한다(서비스 정책은 사업 영역). |
| 백그라운드 작업이 중복 실행되어 후보가 두 번 쌓임 | 작업 멱등성(캐시 키 기준 중복 방지). |

- 12.5의 "배포, 데이터 삭제, 권한 변경은 명시적 승인" 원칙에 동의한다. 운영 환경 마이그레이션도 같은 범주에 넣을 것을 제안한다.

## 12. 누락되었거나 모호한 요구사항

개발 착수 전에 답이 필요한 항목이다. 기획 쪽 결정이 필요한 것은 그렇게 표시했다.

1. **AI 제공 방식 (BYOK vs 운영자 모델):** 아키텍처(키 보관, 정산, 모델 품질 편차)가 달라진다. MVP는 하나만 고르기를 권한다. 결정은 사업 영역.
2. **승인 단위:** 진술 하나씩인가, 개체 단위 일괄인가. 2.5의 검토 피로 문제와 직결된다.
3. **"자동 승인 규칙"(3.2)의 정의:** 어떤 조건으로 무엇을 자동 확정하는지 없다. MVP 제외를 권하지만, 남긴다면 정의가 필요하다.
4. **회차 분할 규칙:** 한 파일에 여러 회차가 들어 있을 때 경계를 무엇으로 인식하는지, 분할 결과를 사용자가 확인·수정하는 단계가 있는지.
5. **"사건"의 단위:** 장면인가, 회차 내 사건인가, 작가가 정의하는가. 연표와 시뮬레이터 태그 모두 이 정의에 의존한다.
6. **시간 정밀도:** 날짜·상대 시간·불명확 기간 중 MVP에서 무엇을 지원하는지.
7. **화자 판별 요구 수준:** 6.2는 "인물 발언"을 따로 기록하라고 하지만, 대사 화자 판별 정확도는 **[미확인]**이다. 판별 실패 시 기본값을 "서술"로 할지 "미상"으로 할지 정해야 한다.
8. **정확도 목표:** 추출 정밀도·재현율, 충돌 경고 유효율의 목표치가 없다. PoC 통과 기준이 되어야 한다.
9. **비기능 요구:** 지원할 최대 원고 규모(예: 1,000화?), 일괄 분석 허용 소요 시간, 동시 사용자 수 가정이 없다.
10. **내보내기 "표준 형식"(6.1):** 구체적 형식이 없다. 제안: 전체 데이터 JSON(재가져오기 가능) + 위키 Markdown + 표 CSV.
11. **시뮬레이션 실행 중 원고 수정:** 실행 시점의 원고 버전을 고정(스냅샷)하는 것으로 정할 것을 제안한다.
12. **고자극·성인 콘텐츠 정책:** 분석 대상 허용 범위, 댓글 공격성 상한(4.7), 공급사 정책과의 충돌. 정책은 사업 영역, 거부 처리는 개발 영역.
13. **승인 취소(undo):** 잘못 승인한 진술을 되돌리는 방법과 그 이력 표시. ChangeLog로 기술적으로는 가능하나 요구사항에 없다.
14. **시리즈·공유 세계관의 ID 범위:** 3차 기능이지만 개체 소속 범위를 지금 정하지 않으면 나중에 마이그레이션 비용이 크다.
15. **다국어(2.1):** 확장 시 검색·별칭 정규화·태그 추출 프롬프트가 언어별로 달라진다. 지금은 한국어 전용으로 설계하되 언어 코드를 프로젝트 속성으로 저장해 둔다.
16. **테스트 원고의 저작권과 확보 경로:** 10.7·11.1이 수백 화 테스트를 요구하지만 원고 출처가 정해져 있지 않다.

### 영역 밖 항목 (한 줄 언급만)
- 검토 대기열과 대량 후보 일괄 처리 화면 설계는 Gemini 담당 영역이다.
- 태그 분류표·기본 페르소나 가중치의 내용, 요금제와 무료 한도, 원고 보관·삭제 정책은 GPT·참깨빙수 결정 사항이다.
