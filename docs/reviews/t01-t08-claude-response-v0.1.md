## T01 승인 상태와 근거 재검토 상태의 분리 — 동의, 의견서 수정

**문제 인정.** 의견서 §0·§5.1의 불변식 2("워커는 확정 진술의 상태를 '재검토 필요'로 바꿀 수 있다")는 "워커는 후보만 쓴다"는 규칙과 충돌한다. 상태 필드 하나에 작가의 판단과 시스템의 관찰을 함께 담았기 때문이다. 불변식 2를 철회하고 다음으로 바꾼다.

**두 축 모델.**

| 축 | 값 | 바꿀 수 있는 주체 |
|---|---|---|
| 승인 상태 `approval` | 후보 · 확정 · 기각 · 승인 취소됨 | 작가의 명시적 행동만 |
| 근거 상태 `evidence_health` | 정상 · 재검토 요청 · 위치 후보 있음 · 유실 | 시스템(워커)이 관찰 결과로 갱신 |

- 워커는 `ReviewRequest`(대상 진술, 원인, 관찰한 판본, 생성 작업 ID)를 **추가**만 한다. 확정 진술의 `approval`은 건드리지 않는다.
- 화면에서 "확정 + 재검토 요청"은 정상적인 조합이다. 확정은 유지되고 경고만 붙는다.

**승인 행동의 동시성.** 승인·기각·취소 요청은 작가가 보고 있던 값을 함께 보낸다.

```
ApproveCommand {
  statement_id, expected_statement_revision,   // 작가가 본 진술 리비전
  reviewed_chapter_version_id,                 // 작가가 본 판본
  actor_id, reason?, batch_id?
}
```

- 서버는 현재 리비전·현재 판본과 다르면 반영하지 않고 "오래된 화면"으로 돌려보낸다(낙관적 동시성). V03의 "오래된 판본에서 승인"이 여기서 걸린다.
- 같은 명령의 중복 전송은 명령 ID로 한 번만 반영한다(T04의 멱등성 키와 같은 장치).
- 묶음 승인은 항목별 트랜잭션으로 처리하고 `batch_id`로 묶는다. 일부 실패는 항목별 결과로 돌려준다. 전체 원자 처리는 하지 않는다. 한 항목이 오래되었다고 묶음 전체를 막으면 검토 피로(의견서 §2.5)가 커진다.

**이력.** 상태 변경은 덮어쓰지 않고 `ApprovalEvent`를 추가한다(행위자, 시각, 이전→다음 상태, 사유, 검토한 판본, 이 이벤트가 대체하는 이벤트). 승인 취소는 "확정 삭제"가 아니라 "취소 이벤트 추가"다. 현재 상태는 이벤트의 마지막 값이다.

**Gemini 디자인 v0.2와의 매핑.** 디자인 토큰의 EpistemicStatus 6단계는 출처 종류(서술 사실·인물 발언 등)와 승인 상태를 한 축에 담고 있다. 구현 시 `source_kind × approval` 두 값에서 표시용 단계를 계산하는 함수 하나로 매핑하고, 저장은 두 축으로 한다. 디자인 쪽 수정 필요 여부는 Gemini 영역이라 언급만 한다.

**남는 결정:** D04(진술별 승인과 묶음 승인의 화면). 위 모델은 D04의 어느 안에도 맞는다.

## T02 근거 앵커의 재현성 — 동의, 구체화

GPT 제안대로 정한다. 의견서 §5.2를 아래로 대체한다.

- **두 해시:** `raw_sha256`(업로드한 원본 바이트), `norm_sha256`(정규화 텍스트).
- **정규화 규칙 v1:** BOM 제거, CRLF·CR → LF, 유니코드 NFC. 공백 축약·문장부호 변환은 하지 않는다(인용이 원문과 달라지므로). 규칙에 버전 번호를 붙이고 앵커에 기록한다.
- **오프셋 단위:** 정규화 텍스트의 **유니코드 코드 포인트** 인덱스, 반열린 구간 `[start, end)`. 브라우저 문자열은 UTF-16이라 이모지에서 어긋나므로 화면 하이라이트 직전에만 변환한다. V02의 이모지·자모 사례가 이 변환을 검사한다.
- **앵커 저장:** 판본 ID, 구간, 정확 인용, 앞뒤 문맥(각 32 코드 포인트), 정규화 규칙 버전. W3C TextQuoteSelector + TextPositionSelector 조합이다.
- **새 판본 재고정:**
  1. 같은 문단 해시 + 같은 상대 위치 → 위치만 옮긴다.
  2. 정확 인용이 **한 곳**에만 있고 앞뒤 문맥도 맞음 → 위치 후보로 기록하고 자동 이동.
  3. 정확 인용이 여러 곳이거나(F2·F3의 동일 인용), 문맥이 다르거나, 유사 일치만 있음 → **자동 이동하지 않는다.** `위치 후보 있음` 상태로 후보 목록을 남기고 작가 확인을 요구한다.
  4. 후보 없음 → `유실`. 진술은 그대로, 근거 상태만 바뀐다(T01).
- 의견서 §5.2 3단계("유사도 기준 이상이면 옮긴다")를 철회한다. 유사 일치를 자동 적용하면 F3에서 미라의 근거가 도윤의 문장으로 옮겨 가는 오류가 생긴다.
- **화자:** 추출 결과의 화자는 `알 수 없음`을 정상 값으로 둔다. 발언 기록은 서술 사실로 자동 승격하지 않는다(V02).

## T03 명부 없는 입력과 충돌 경고 조건 — 동의, 의견서 수정

- 의견서 §4.2 3단계는 "작가가 명부를 확정한 뒤 2단계 추출"이었다. 이를 선택 사항으로 바꾼다. 명부가 없거나 일부만 있어도 추출은 돌고, 연결되지 않은 이름은 `미해결 언급`으로 남는다.
- 별칭·동명이인·호칭의 병합은 자동으로 하지 않고 제안만 한다. 기본값은 보류다.
- **충돌 경고는 네 조건이 모두 있을 때만 낸다:** 같은 개체 ID, 같은 정규화 속성, 비교 가능한 작중 시점(구간이 겹침), 양쪽 근거. 시점을 모르면 경고 대신 "시점 미상" 정보로 표시한다. F4(8년 봄 정상 변경)는 시점이 겹치지 않아 경고 0건, F5(7년 봄 회상)는 F1과 시점이 겹쳐 경고 1건이 된다.
- **의도적 전개 예외**는 작품·근거 쌍·작중 시간 범위에 묶는다. 예외에 쓰인 근거가 새 판본에서 바뀌면 예외도 재검토 요청 대상이 된다. 속성 전체를 끄는 예외는 만들지 않는다.

## T04 캐시 무효화와 작업 멱등성 — 동의, 구체화

의견서 §5.3의 캐시 키 `(본문 해시, 프롬프트 버전, 모델)`는 부족하다는 지적에 동의한다. 세 장치를 분리한다.

**① 입력 스냅샷 해시 = 결과 캐시 키.** 모델에 실제로 들어가는 모든 것을 정규 JSON(RFC 8785 JCS)으로 직렬화해 SHA-256을 낸다.

```
InputSnapshot {
  scope:    { owner_id, work_id }                 // 다른 소유자 캐시 적중 0건(V05)
  target:   { chapter_id, chapter_version_id, norm_sha256 }
  order:    [chapter_version_id ...]              // 판본 순서
  context:  { roster_revision, prior_summary_ids+hashes, promise_profile_revision }
  pipeline: { job_type, normalizer_ver, parser_ver, schema_ver, prompt_ver }
  model:    { provider, model_snapshot_id, options }   // 별칭(예: latest) 금지, 고정 스냅샷 ID
}
```

- 같은 해시면 다시 호출하지 않고 저장된 결과를 쓴다. 어느 필드든 바뀌면 자연히 적중하지 않는다. "무효화 목록"을 따로 관리하지 않아도 된다.
- 모델 이름에 별칭을 쓰면 공급사가 대상 모델을 바꿔도 해시가 같아 캐시가 틀린다. 고정 스냅샷 ID만 허용한다.

**② 실행 멱등성 키.** "같은 사용자 명령이 두 번 실행되지 않게" 하는 장치다. `(job_type, target, input_snapshot_hash, command_id)`. 재시도는 같은 키를 쓴다. 키가 같은 작업이 이미 진행 중이면 새로 만들지 않고 기존 작업을 돌려준다. 고유 결과 1건(V04)이 여기서 보장된다.

**③ 결과 반영 조건(펜싱).** 결과가 도착했을 때 "현재 상태에 반영해도 되는가"를 별도로 확인한다.

- 작업은 시작할 때 `base_version`(대상의 현재 판본)과 `generation`(대상별 증가 번호)을 받는다.
- 반영은 조건부 갱신이다: 대상의 현재 판본 = `base_version`이고, 작업이 취소되지 않았고, 더 큰 `generation`의 결과가 반영되지 않았을 때만.
- 조건이 맞지 않는 늦은 결과는 버리지 않고 "구판 결과"로 저장만 한다(비용·감사 기록). 현재 결과를 덮은 사례 0건(V04)이 여기서 보장된다.
- 취소는 종료 상태다. 취소 뒤 도착한 응답도 같은 규칙으로 저장만 한다.

**왜 셋으로 나누나.** ①은 "이미 계산한 것을 다시 사지 않기", ②는 "같은 명령을 두 번 실행하지 않기", ③은 "늦게 온 옛 결과가 새 상태를 덮지 않기"다. 하나의 키로 합치면, 예를 들어 같은 입력을 새 명령으로 일부러 재실행하려는 경우(②는 다르고 ①은 같음)나, 입력은 같지만 그 사이 대상이 다른 판본으로 넘어간 경우(①은 같고 ③은 거부)를 구별할 수 없다.

## T05 가상 독자 수치의 재현 계약 — 동의

**설계 검산 결과.** PoC 검증 계획의 2집단 표(순애 6,000 / 피폐 4,000, G2 → B2 → C2+R1 → H2)를 문서의 식으로 독립 재계산했다. 4개 회차의 집단별 이탈률·잔류 인원, 전체 잔류, 누적 잔존율, 연속 열람률이 표의 자릿수까지 모두 일치했다. 2화 순애 집단의 B 제거 반사실 이탈률 4.9460%도 일치했다. 외부 호출 없는 로컬 계산이며, 문서 산식 대조이므로 검증 계획의 분류대로 **설계 검산**으로 기록한다(제품 코드 아님).

- 재계산 때 해석한 부분: "순애 집단 지시값"을 순애 1, 피폐 0으로 읽었다. 이렇게 읽어야 표가 맞는다.
- **제안:** 이 값을 집단 이름에 묶지 말고 집단 프로필의 매개변수(예: `betrayal_trust_sensitivity`)로 두자. 그래야 집단을 추가해도 식을 고치지 않는다. 가중치 표 버전과 함께 저장한다.

**재현 계약.**

- 수치는 동결 입력(태그 스냅샷, 판본 순서, 집단 프로필·가중치·커널 버전, 시드, 난수 알고리즘 이름과 버전)의 결정적 함수다. 같은 입력이면 20/20 동일(V10).
- 부동소수는 IEEE 754 배정밀도, 중간 반올림 없음, 표시할 때만 반올림. `Math.random`은 시드를 줄 수 없으므로 섭동이 들어가면 시드 가능한 알고리즘을 명시해 고정한다.
- 댓글·감평 문장(LLM 출력)은 재계산하지 않고 저장된 결과 스냅샷을 다시 보여 준다. 수치와 댓글의 실패·재시도를 따로 둔다.
- 태그 영향 표시는 "이 태그를 뺐을 때의 차이(반사실)"로만 쓰고 "기여도 합"으로 쓰지 않는다. 비선형이라 더해지지 않는다는 검증 계획의 지적에 동의한다.

## T06 비용 예약·계측·동의 재확인 — 동의, 일부 보류

- **예약:** 호출 전 `입력 토큰 추정 + max_output_tokens` 상한으로 최대 비용을 계산해 예약하고, 상한을 넘으면 발송하지 않는다. 출력 상한은 지금 알파처럼 설정 한 곳(`src/review/config.ts`에 해당하는 위치)에서 관리한다.
- **계측:** 작업마다 응답의 사용량 필드(입력·캐시 입력·출력·추론 토큰), 지연, 재시도·거부·실패를 기록한다. 원문·인용·키는 기록하지 않는다(V05).
- **동의 재확인:** 큐에 넣을 때가 아니라 **HTTP 요청 직전**에 워커가 (공급사, 모델, 데이터 범위) 동의 버전을 다시 확인한다. 자동 대체 모델 경로는 코드에 두지 않는다. 미승인 모델 호출 0건은 송신 허용 목록(서버의 아웃바운드 허용 목록, 알파의 CSP `connect-src`에 해당)으로 한 번 더 막는다.
- **보류:** 실제 청구 금액과 작업별 예상치의 대조. 공급사의 사용량·청구 API가 작업 단위 대조를 지원하는지 확인한 뒤 정한다. 지원하지 않으면 일 단위 총액 대조로 낮춘다.

## T07 삭제·백업·복구 — 원칙 동의, 상세 보류

- 일반 수정은 불변 판본으로 남기고, 승인된 삭제는 대상별 범위표(본문·파생물·캐시·내보내기·백업·공급사 보관)로 정의한다는 제안에 동의한다.
- 복구 후 서비스 연결 전에 **삭제 원장**을 재적용한다. 삭제 원장은 삭제 대상 ID와 시각만 담고 본문은 담지 않는다.
- 백업 안의 개별 삭제는 두 방식 중 하나다. (a) 작품별 암호화 키를 두고 키를 폐기하는 방식(백업을 건드리지 않고 복호 불가로 만듦), (b) 백업 보존 기간 만료를 기다리고 복구 때 삭제 원장을 재적용하는 방식. (a)는 키 관리 비용이, (b)는 보존 기간 동안의 잔존이 단점이다. 보존 기간과 공급사 보관 정책은 D03·데이터 정책 영역이라 **보류**한다.

## T08 스택은 구현 가설 — 동의

- 웹·TypeScript·PostgreSQL·별도 워커를 비교 기준안으로 두고, 측정 뒤 선택한다는 데 동의한다.
- **제안:** E0(로컬·무호출)의 핵심 로직은 DB·웹 프레임워크와 무관한 순수 TypeScript 모듈로 만든다. 정규화·앵커 재고정(T02), 승인 이벤트 적용(T01), 입력 스냅샷 해시·펜싱(T04), 독자 수치 커널(T05)이 대상이다. 저장소 계층은 인터페이스로 두고 E0에서는 메모리 구현만 쓴다. 이러면 스택 결정과 E0 착수가 서로를 기다리지 않는다.
- 알파의 Vite + React + TypeScript는 알파 한정 선택이며 본 제품 스택 결정과 별개다.

## 알파에서 얻은 개발 근거 (D03 참고용)

- 2026-11-22 참깨가 배포 주소에서 실키로 감평을 실행해 OpenAI 응답 텍스트가 화면에 표시되는 것을 확인했다(A05 통과). 성공 응답은 브라우저가 읽을 수 있었다.
- 반면 잘못된 키의 401 응답에는 CORS 허용 헤더가 없어, 브라우저 직접 호출 구조에서는 인증 실패를 "네트워크 오류"와 구별하지 못한다. OpenAI도 키를 브라우저에 두지 말라고 권고한다.
- 따라서 여러 사용자가 쓰는 제품에서 BYOK를 택하더라도 키는 서버(또는 사용자 기기의 로컬 앱)를 거치는 구조가 필요하다는 것이 개발 쪽 판단이다. 브라우저 직접 호출은 개인 검증용 알파에 한정한다. BYOK와 운영자 모델의 선택 자체는 D03(사업 결정)이다.

## E0 착수 준비 (D01 승인 시)

D01에서 권고 A의 무호출 합성 실험이 승인되면 다음 순서로 진행한다. 승인 전에는 착수하지 않는다.

1. 순수 모듈 뼈대와 테스트 러너(위 T08 제안).
2. V01·V02: 판본 추가, 정규화, 앵커 재고정, 검증 계획의 F1–F5 합성 문장과 변형(문단 삽입, 동일 구간, 조합형/분해형, CRLF·BOM, 이모지).
3. V03: 승인 이벤트, 낙관적 동시성, 묶음 일부 실패.
4. V04: 입력 스냅샷 해시, 멱등성 키, 펜싱(늦은 완료·취소 시나리오).
5. V10: 독자 수치 커널, 위 검산표를 기대값으로 고정, 20회 반복 동일성.
6. 결과 기록은 검증 계획의 "실행 기록 항목" 형식으로 남긴다. 조건 변경은 결과를 보기 전에 기록한다.

V05–V08(격리·동의·복구·위험 입력)은 저장소·서버 계층이 필요해 스택 선택 뒤로 둔다. V09·V11·V12는 모델·사용자 검증(E1·E2)이다.
